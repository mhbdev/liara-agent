# ۳. ایجنت‌ها — هر کدام چه کاری می‌کنند

شش نقش. هر کدام کار محدودی دارد، و مرزهای بینشان طراحی امنیتی است، نه
بوروکراسی.

```
                        ┌──────────────────┐
      «ورود» ──────────►│      اتصال       │  حساب و رمزها،
                        │    CONNECT       │  به‌صورت گفت‌وگویی
                        └────────┬─────────┘
                                 │
                        ┌────────▼─────────┐
     بار اول ──────────►│    راه‌اندازی     │  liara.json،
                        │   ONBOARDING     │  OPERATIONS.md
                        └────────┬─────────┘
                                 │
      ┌──────────────────────────┼──────────────────────────┐
      │                          │                          │
┌─────▼──────┐          ┌────────▼────────┐        ┌────────▼────────┐
│    پایش     │          │     انتشار      │        │  مشاور منابع     │
│    SRE     │          │     DEPLOY      │        │  PLAN ADVISOR   │
│ فقط خواندن  │          │  با تأیید و اثبات │        │  قیمت زنده       │
└─────┬──────┘          └────────▲────────┘        └─────────────────┘
      │ مشکل پیدا شد             │ فقط محیط آزمایشی
      │                          │ (اصلی نیاز به تأیید انسان دارد)
┌─────▼──────────────────────────┴──┐
│          عیب‌یابی و تعمیر           │
│  مدرک ← علت ← تست شکست‌خورده ← وصله  │
│  هرگز روی محیط اصلی منتشر نمی‌کند     │
└───────────────────────────────────┘
```

## اتصال — «ایجنت ورود و اتصال حساب»

`.claude/agents/liara-connect.md` · `/liara-login`

**همان یک ایجنتی که برای ورود با آن حرف می‌زنید.** لازم نیست بدانید
`doctor.sh`، `creds.sh` و `setup.sh` وجود دارند — شما می‌گویید «ورود» و او همه
کار را پیش می‌برد: دستگاه را بررسی می‌کند، تست خودکار قفل امنیتی را اجرا
می‌کند، برای آن یک قدمی که به کیبورد شما نیاز دارد یک تب ترمینال باز می‌کند،
نتیجه را تأیید می‌کند و می‌گوید در حسابتان چه چیزی هست.

دردسرهای معمول را هم خودش حل می‌کند: توکن منقضی‌شده (رایج‌ترین خطا، و اگر
توضیح داده نشود نگران‌کننده)، قطع دسترسی، و «راه‌اندازی من امن است؟».

**حتی به اشتباه هم نمی‌تواند توکن شما را بگیرد.** `setup.sh connect` به یک
ترمینال واقعی نیاز دارد، پس اگر ایجنتی اجرایش کند کد خروج ۳ می‌گیرد. توکن از
کلیپ‌بورد شما به یک فایل رمزنگاری‌شده روی دستگاه خودتان می‌رود، و ایجنت فقط
`****a1b2` و موفقیت یا شکست دستورها را می‌بیند.

**کِی:** «ورود»، «اتصال حساب»، «کلید API»، رد شدن توکن، اضافه کردن محیط اصلی.

## راه‌اندازی — «دستیار راه‌اندازی پروژه»

`.claude/agents/liara-onboarding.md`

بعد از وصل شدن کار را تحویل می‌گیرد: نوع پروژه را تشخیص می‌دهد، `liara.json`
را می‌نویسد (همیشه با `healthCheck`) و `OPERATIONS.md` را می‌سازد.

**هر بار یک سؤال** می‌پرسد، هر سؤال یک پاسخ پیش‌فرض دارد، پس «نمی‌دانم» همیشه
یک جواب کامل است. در پایان `OPERATIONS.md` را می‌نویسد: چه ساخته، چقدر هزینه
دارد، کدام دستورها مهم‌اند.

**کِی:** اولین راه‌اندازی، منقضی شدن رمز، اضافه کردن یک محیط.

## پایش — «ایجنت پایش و حادثه»

`.claude/agents/liara-sre.md`

به یک سؤال با مدرک جواب می‌دهد: *آیا این سایت الان واقعاً برای کاربرانش کار
می‌کند، و اگر نه، چه چیزی عوض شده؟*

**عمداً فقط خواندنی است.** تشخیص می‌دهد و پیشنهاد می‌کند؛ تعمیر نمی‌کند.

پنج وضعیت، و دو تایی که بیشترین اهمیت را دارند:

| وضعیت | معنی |
|---|---|
| `healthy` | پاسخ ۲xx/۳xx، سرعت در محدوده |
| `slow` | بالاست ولی کندتر از حد مجاز |
| **`flapping`** | بعضی بررسی‌ها موفق، بعضی ناموفق — بدترین حالت برای نادیده گرفتن |
| **`degraded`** | صفحه اصلی سالم، `/health` خراب — کاربر به بخش خراب می‌خورد |
| `down` | همه بررسی‌ها شکست خوردند |

`flapping` و `degraded` دقیقاً همان دو حالتی هستند که خودتان هرگز متوجهشان
نمی‌شوید — و همان‌هایی که «به نظر من که سایت سالمه» را اشتباه می‌کنند.

ترتیب بررسی، از ارزان به گران: چه چیزی عوض شد (معمولاً آخرین انتشار) ← رویدادهای
پلتفرم ← منابع ← وابستگی‌ها ← SSL و DNS ← **تاریخچه خرابی‌های خود این پروژه در
`state/incidents/`**.

**کِی:** «سایت بالاست؟»، «کند شده»، «لاگ‌ها رو ببین»، گزارش روزانه.

## انتشار — «ایجنت انتشار»

`.claude/agents/liara-deploy.md`

منتشر می‌کند، بعد **ثابت می‌کند** که کار کرده.

```
بررسی قبل از پرواز ← نقشه ← تأیید ← انتشار ← راستی‌آزمایی ← گزارش
```

هیچ مرحله‌ای را رد نمی‌کند و ترتیب را عوض نمی‌کند. «بررسی قبل از پرواز» یک
اسکریپت قطعی است، نه قضاوت ایجنت — شش موردی که یک مهندس باتجربه ناخودآگاه چک
می‌کند: تست‌ها، بیلد، جست‌وجوی رمز در تغییرات، سلامت `liara.json`، متغیرهای
محیطی روی سرور، و اینکه آیا نسخه فعلی از قبل خراب نیست.

«منتشر شد» یعنی بررسی سلامت قبول شده. اینکه دستور بدون خطا تمام شود، مدرک
نیست. اگر نتواند تأیید کند می‌گوید «منتشر شد ولی سالم نیست» — و این یعنی سیستم
درست کار می‌کند.

**کِی:** «منتشر کن»، انتشار یک وصله تأییدشده.

## مشاور منابع — «مشاور پلن»

`.claude/agents/liara-plan-advisor.md`

می‌گوید چه بخرید، و استدلالش را نشان می‌دهد.

**قانونی که این ایجنت را تعریف می‌کند: هیچ‌وقت قیمتی را از حافظه نگوید.** لیارا
پلن‌ها و قیمت‌ها را عوض می‌کند؛ یک عدد به‌یادمانده که با اطمینان گفته شود از
«نمی‌دانم» بدتر است، چون شما بر اساسش پول خرج می‌کنید. هر عدد از
`liara plan list` در همان لحظه می‌آید، به‌علاوه مصرف واقعی اپ شما از
`metrics/summary`.

هر عدد برچسب دارد:

- **[measured]** — از مصرف واقعی خود اپ، با ذکر بازه زمانی
- **[estimated]** — از چیزی که شما گفتید، با نوشتن صریح فرض

کل صورتحساب را هم حساب می‌کند — اپ + دیتابیس + دیسک + فضای ابری — چون دیتابیس
معمولاً رقم بزرگ‌تر و همان سورپرایز همیشگی است.

**کِی:** «کدوم پلن؟»، «سرورم کوچیکه؟»، «هزینه هاستم زیاده».

## عیب‌یابی و تعمیر — «ایجنت عیب‌یابی»

`.claude/agents/liara-debug-fix.md`

علت را از روی مدرک پیدا می‌کند و وصله‌ای آماده می‌کند که یک انسان در دو دقیقه
بتواند بازبینی کند.

**خروجی‌اش یک وصله است، نه تغییر روی محیط اصلی.** این مهم‌ترین مرز کل پکیج
است. تمام سرعت تشخیص و وصله خودکار را دارید، و هیچ‌کدام از ریسک ایجنتی که وسط
یک خرابی به محیط اصلی دسترسی نوشتن دارد.

روش: اول بازتولید کن، بعد نظریه بده ← بازه محدود از مدارک ← دسته‌بندی ←
**برای هر ادعا مدرک نقل کن** ← علت‌ها را با درجه اطمینان رتبه‌بندی کن ←
**اول تست شکست‌خورده بنویس** ← کوچک‌ترین تغییری که علت را درمان کند ←
راستی‌آزمایی ← یادداشت تحویل.

این‌ها را رد می‌کند: مهاجرت مخرب دیتابیس برای اینکه اپ بالا بیاید؛ دستکاری
محافظ‌های خودش برای عبور از یک مسدودسازی؛ ادعای «درست شد» بدون اجرای تست؛
درست کردن چند چیز در یک وصله.

**کِی:** «چرا خرابه؟»، «درستش کن»، انتشار ناموفق، بعد از اینکه ایجنت پایش چیزی
پیدا کرد.

## چرا این جداسازی

| مرز | جلوی چه چیزی را می‌گیرد |
|---|---|
| پایش فقط خواندنی است | بررسی‌ای که ناخواسته چیزی را عوض کند |
| ایجنت تعمیر نمی‌تواند روی محیط اصلی منتشر کند | همان خطای منتشرشده‌ای که در دنیای واقعی رخ داده: ایجنتی که وسط خرابی روی production می‌نویسد |
| انتشار نمی‌تواند بررسی قبل از پرواز را رد کند | فرستادن نسخه خراب چون «عجله داشتیم» |
| مشاور پلن نمی‌تواند قیمت حافظه‌ای بدهد | مشاوره‌ی مطمئنِ غلط که پول واقعی خرج می‌کند |
| فقط ایجنت اتصال با رمز کار دارد | پنج ایجنتی که می‌توانستند رمز را لو بدهند، در برابر یکی که حتی نمی‌تواند به آن برسد |
