# ۵. دفترچه بحران — سایت خراب شده، حالا چه کنم

وقتی چیزی خراب است از اینجا شروع کنید. هر بخش: چه می‌بینید ← چه کنید ← به ایجنت
چه بگویید.

**قانون هر خرابی: اول سرویس را برگردان، بعد بفهم چه شده.** یک rollback که کار
می‌کند از یک تشخیصِ هنوز نیمه‌تمام بهتر است.

---

## سایت کاملاً پایین است

**چه می‌بینید:** هیچ چیز بالا نمی‌آید، تایم‌اوت، یا صفحه خطای لیارا.

```bash
sh scripts/health.sh https://your-site.ir "" 3
```

یا فقط بگویید: **«سایت بالا نمیاد»**.

بعد به ترتیب:

۱. **اخیراً انتشاری انجام شده؟** بیشتر وقت‌ها جواب همین است.
   ```bash
   LIARA_ENV=staging sh scripts/liara.sh app logs --app YOUR-APP --since "1 hour ago" --timestamps
   ```
   اگر اولین خطا چند دقیقه بعد از یک انتشار است — **همین الان برگردید به نسخه
   قبل**، تشخیص بماند برای بعد.

۲. **اصلاً اپ در حال اجراست؟**
   ```bash
   LIARA_ENV=staging sh scripts/liara.sh app list
   ```
   متوقف است → روشنش کنید:
   ```bash
   LIARA_ENV=staging sh scripts/liara.sh app start --app YOUR-APP
   ```

۳. **حافظه یا دیسک تمام شده؟** `GET /v1/projects/{name}/metrics/summary` مقادیر
   `cpuUsage`، `memoryUsage` و `disksUsage` را می‌دهد. کمبود حافظه به شکل
   ری‌استارت‌های پشت سر هم بدون پیام خطا دیده می‌شود. دیسک پر به شکل خطای نوشتن.

۴. **رویدادهای پلتفرم** — `GET /v1/projects/{name}/events` ری‌استارت‌ها، kill
   شدن به خاطر حافظه و انتشارهای ناموفق را نشان می‌دهد؛ چیزهایی که در لاگ خود
   اپ اصلاً نیستند.

۵. **باز هم هیچی؟** وضعیت خود لیارا را ببینید، و مطمئن شوید دامنه و گواهی SSL
   منقضی نشده‌اند (`health.sh` تعداد روز باقیمانده SSL را می‌گوید).

---

## سایت بالا می‌آید ولی خراب است

**چه می‌بینید:** صفحه اصلی سالم، ولی ورود / پرداخت / جست‌وجو کار نمی‌کند.

این همان `degraded` است، و همان حالتی که «به نظر من که سالمه» را اشتباه می‌کند.
پاسخ ۲۰۰ از صفحه اصلی **مدرک نیست** که اپ کار می‌کند.

```bash
sh scripts/health.sh https://your-site.ir /api/health 3
```

بگویید: **«سایت باز میشه ولی فلان کار نمی‌کنه»**.

رایج‌ترین علت‌ها، به ترتیب:

| علت | نشانه | راه‌حل |
|---|---|---|
| متغیر محیطی گم‌شده | `undefined` یا `KeyError` روی تنظیمات | `liara env set` |
| دیتابیس در دسترس نیست | تایم‌اوت یا خطای احراز هویت در اولین کوئری | بررسی روشن بودن دیتابیس و درستی رمز |
| مهاجرت انجام‌نشده | بالا می‌آید ولی هر مسیر دیتابیسی ۵۰۰ می‌دهد | مهاجرت را **آگاهانه** و با بکاپ اجرا کنید |
| کلید سرویس خارجی منقضی شده | ۴۰۱/۴۰۳ از یک API بیرونی | آن کلید را عوض کنید |
| دیسک پر | خطای آپلود یا نوشتن | دیسک را خالی یا بزرگ کنید |

---

## سایت کند شده

```bash
SLOW_MS=1500 sh scripts/health.sh https://your-site.ir "" 5
```

پنج بررسی، چون یک پاسخ کُند فقط نویز است.

بعد از ایجنت بخواهید با آخرین انتشار مقایسه کند. علت‌های معمول: کوئری بدون
ایندکس، حلقه‌ای که برای هر سطر یک کوئری می‌زند (N+1)، پلن کوچک (قبل از خرید
`metrics/summary` را ببینید)، یا یک API خارجی کُند.

بگویید: **«سایت کند شده»**.

---

## انتشار شکست خورد

**چه می‌بینید:** دستور انتشار خطا داد، یا `healthCheck` نسخه را رد کرد.

**این یعنی سیستم درست کار می‌کند.** بخش `healthCheck` در `liara.json` دروازه
انتشار است: اگر بررسی سلامت رد شود، انتشار شکست می‌خورد و نسخه خراب هرگز به
کاربر سرویس نمی‌دهد.

```bash
LIARA_ENV=staging sh scripts/liara.sh logs --app YOUR-APP --since "20 minutes ago" --timestamps
```

| نشانه | علت معمول |
|---|---|
| خطا قبل از بالا آمدن اپ | شکست بیلد — کد یا دستور بیلد را درست کنید |
| بالا می‌آید ولی health check تایم‌اوت می‌شود | `port` در `liara.json` با پورت واقعی اپ یکی نیست |
| `module not found` | مشکل وابستگی یا lockfile |
| `undefined` روی یک مقدار تنظیمات | متغیر محیطی گم‌شده |

بگویید: **«دیپلوی خطا داد»** — ایجنت عیب‌یابی لاگ‌ها را می‌خواند و مدرک نقل
می‌کند.

---

## برگشت به نسخه قبل (rollback)

معمولاً درست‌ترین اولین حرکت در یک خرابی.

```bash
# بررسی یک نسخه سالم شناخته‌شده
LIARA_ENV=staging sh scripts/liara.sh app logs --app YOUR-APP -r v11
```

برگشت روی محیط اصلی نیاز به تأیید انسان دارد:

```bash
sh scripts/approve.sh grant rollback
```

بگویید: **«برگرد به نسخه قبلی»**.

---

## مشکل دیتابیس

**قبل از هر کاری، بکاپ بگیرید:**

```bash
LIARA_ENV=staging sh scripts/liara.sh db backup create
LIARA_ENV=staging sh scripts/liara.sh db backup list
```

**ایجنت‌ها از اجرای `DROP`، `TRUNCATE` یا مهاجرت مخرب برای بالا آوردن اپ
خودداری می‌کنند.** این امتناع عمدی است — از دست دادن داده یک استراتژی انتشار
نیست. مهاجرت نیاز دارد به: یک بکاپ تازه، یک مسیر برگشت تست‌شده، و یک انسان که
اجرایش کند.

---

## خواندن پیام «BLOCKED»

```
BLOCKED by scripts/guard.sh: production write without approval
```

این باگ نیست. ایجنت کاری را خواسته که نیاز به رضایت صریح شما دارد. پیام دقیقاً
می‌گوید چه کنید. اگر با آن کار موافقید:

```bash
sh scripts/approve.sh grant prod-write
```

یک‌بار مصرف، ۱۵ دقیقه. اگر **نمی‌فهمید** می‌خواست چه کند، قبل از تأیید از او
توضیح بخواهید. همین مکث، تمام ارزش این دروازه است.

---

## بعد از هر خرابی — فقط همین یک کار

بنویسیدش. یک فایل، پنج دقیقه:

`state/incidents/YYYY-MM-DD-short-slug.md`

- چه دیدید
- واقعاً چه بود
- چه چیزی درستش کرد
- چه چیزی دفعه بعد ۱۰ برابر سریع‌تر پیدایش می‌کرد

ایجنت پایش **قبل از هر تشخیص جدید این پوشه را می‌خواند.** تا خرابی بیستم،
اولین حدسش بر پایه تاریخ واقعی سیستم خودتان است، نه استدلال کلی. این تنها بخشی
از پکیج است که با گذشت زمان **بهتر** می‌شود — و تنها بخشی که به شما وابسته است.

---

## اضطراری: همه‌چیز را متوقف کن

```bash
LIARA_ENV=production sh scripts/liara.sh app stop --app YOUR-APP   # نیاز به تأیید
sh scripts/approve.sh revoke-all                                    # لغو همه تأییدها
```

فعال کردن **حالت فقط‌خواندنی** روی اپ
(`POST /v1/projects/{id}/read-only/enable`) ترمز ملایم‌تری است: سایت سرویس
می‌دهد، ولی هیچ چیزی نمی‌تواند بنویسد.
